# Reacher runner 差异与验收清单

这份清单只描述 vanilla LeWM Reacher 与共享 scheduler 的接入参数。不要从本地 `fast-lewm-pusht` 的 Reacher YAML 导入 planner 配置；它是另一种模型与评估方案。

- Keep `world.env_name=swm/ReacherDMControl-v0`, `world.task=qpos_match`, seed `42`, `num_eval=50`, `goal_offset_steps=25`, `eval_budget=50`, image size `224`, and dataset name `dmc/reacher_random`.
- Keep callables: restore the initial `qpos` and `qvel` with `set_state`, then set the future target `goal_qpos` with `set_target_qpos`.
- Keep vanilla plan configuration `horizon=5`, `receding_horizon=5`, `action_block=5`; the pinned policy action buffer spans 25 wrapper control ticks (`5 × 5`). A control tick here is one `EnvPool.step`/Reacher wrapper step. Pinned [`DMControlWrapper`](https://github.com/galilai-group/stable-worldmodel/blob/10c26dbd5677083fa31dba69eb738b973845e9a4/stable_worldmodel/envs/dmcontrol/dmcontrol.py) exposes `action_repeat=2` and repeats each action twice; `ReacherDMControlWrapper` constructs the underlying [`dm_control` environment](https://github.com/galilai-group/stable-worldmodel/blob/10c26dbd5677083fa31dba69eb738b973845e9a4/stable_worldmodel/envs/dmcontrol/reacher.py). Do not report K as physics substeps. At runtime, read underlying `control_timestep()` and multiply by the wrapper's actual repeat metadata; if either is unavailable, true-async pacing must stop until a verified repeat is explicitly frozen.
- Keep official image/action/state transforms, CEM `300/30/30`, solver seed behavior, success rule, and budget. Do not import the Fast-LeWM YAML (`horizon=1`, five action blocks, different checkpoint) into this baseline.

## Task identity, batching, and slicing

- Make the 50-task manifest once from the vanilla evaluator's seed-42 sampling procedure after assets are ready on a compute allocation. Persist ordered dataset row, episode ID, start step, and goal step (`start_step + 25`). All arms read this manifest; no arm independently resamples. The official sampler selects dataset rows, so repeated episode IDs are possible.
- Preserve the upstream sampling details exactly: valid start rows leave `goal_offset_steps=25`; `eval_budget` limits rollout length and is not an extra sampling filter. Use the pinned evaluator's RNG and ordering (including its `choice(len(valid_indices)-1, ...)` behavior), then sort selected dataset rows as upstream does. Record both selected row and episode/start-step because repeated episodes may otherwise obscure task identity.
- Preserve the strict order `freeze-manifest → batch50-k0 → n1-k0 → fixed/async`. The complete batch-50 result is a config/task-validity gate for N=1; Reacher has no independent frozen per-task success vector, so do not claim external item-wise outcome equality. The N=1 K=0 result is the paired baseline for fixed-delay and true-async. Neither gate uses a success-rate threshold.
- `runner.py` accepts `--task-start` and `--task-count` (1–50) for N=1 arms and writes one task JSON plus a slice summary. One process loads the HDF5 and model once, then creates a fresh policy/CEM per manifest task. Disjoint N1 K0 slices can be supplied as repeated `--n1-k0-gate` summary paths; fixed/async validate that the summaries and task files cover all 50 manifest identities exactly once.
- Paired N=1 seeds are `42 + manifest_order` across K=0, fixed K, and true-async; this is distinct from the original batch-50 RNG stream. Each result records task identity, planner seed, metrics, tick/action-space metadata, and scheduler events. Async summaries report first-call latency, later planning overlap in control ticks, and native-buffer action counts.
- CLI modes are `batch50-k0`, `n1-k0`, `fixed_steps`, and `true_async`. N1 and delay modes require a complete `--batch50-gate`; fixed/async additionally require one or more complete `--n1-k0-gate` summaries. `fixed_steps` takes `--delay-steps` from `{1,2,4,8,16}`; K=0 remains the direct native synchronous path. `reacher/run_eval.pbs` exposes the same modes and task slicing, writes 5-second GPU telemetry to `job.log`, and records `job_status`.

## Adapter boundary and runtime prerequisites

- The shared scheduler is `../pusht/adapter.py`; Reacher supplies verified DMC tick metadata and a neutral action computed from the live action-space bounds. The runner fails closed unless the finite bounds' midpoint is exactly zero within `1e-12`, and passes that checked value to the shared adapter.
- Reacher's first async solve has no action buffer. Start solve on the worker at reset and immediately advance using environment-space zero; once a plan exists, apply its first action. Later replans are requested when the native action buffer is empty; while inference is pending, repeat the last physical environment action (zero only at startup), then install the result on the control thread. Never call the mutable `WorldModelPolicy.get_action` from the solver worker; snapshot inputs on the control thread and install returned plan/buffer state on the owner thread according to the pinned policy implementation.
- The already present ASPIRE venv was missing both `mujoco` and `dm_control`; the CPU prep job is expected to provide them. The vanilla Reacher checkpoint/data were absent in the earlier lightweight stat: expected assets are `$STABLEWM_HOME/reacher/lewm_object.ckpt` and `$STABLEWM_HOME/dmc/reacher_random.h5`, with source weights/config staged separately. Confirm these paths and the installed imports in the PBS job before any model run.
- Existing local `experiment/reproduction/fast-lewm-pusht/upstream/config/eval/reacher.yaml` is Fast-LeWM-specific (`Fast-lewm_weights.ckpt`, horizon 1, action blocks 5×5). It is not evidence of a runnable vanilla checkpoint or vanilla Reacher baseline.

## Source and asset pins

- Vanilla model repo [`quentinll/lewm-reacher`](https://huggingface.co/quentinll/lewm-reacher), revision `62adae4b71dc474ddf8f794c476ebfe737a743ca`; source files `config.json` and `weights.pt` are converted using the pinned LeWM README procedure.
- Vanilla dataset repo [`quentinll/lewm-reacher` dataset](https://huggingface.co/datasets/quentinll/lewm-reacher), revision `e70a080d0d04c6072123c9ebd343acf7fff28dbf`; archive `reacher.tar.zst` should extract to `$STABLEWM_HOME/dmc/reacher_random.h5`.
- The pinned `HDF5Dataset(name, cache_dir=...)` resolves names under `<cache_dir>/datasets/<name>.h5`; therefore it opens `$STABLEWM_HOME/datasets/dmc/reacher_random.h5`. The GPU wrapper points `STABLEWM_HOME` at a job-private cache and symlinks the staged checkpoint/HDF5 there. The runner then creates or verifies the pinned `datasets/dmc/reacher_random.h5` link only after its PBS compute guard.
- This path rule is implemented in pinned [`HDF5Dataset.__init__`](https://github.com/galilai-group/stable-worldmodel/blob/10c26dbd5677083fa31dba69eb738b973845e9a4/stable_worldmodel/data/formats/hdf5.py#L32-L53).
- The converted `lewm_object.ckpt` is a serialized full model object; runner model loading uses `torch.load(..., weights_only=False)` from the explicit asset path. Hydra `policy` remains `reacher/lewm` as the run name, without a `.ckpt` suffix. The pinned stable-worldmodel `load_pretrained` loader expects a `.pt` state dict plus `config.json`, so it must not be used for this converted object checkpoint.
- Upstream conversion and dataset instructions: [pinned LeWM README](https://github.com/lucas-maes/le-wm/blob/8edfeb336732b5f3ce7b8b210d0ba370a09e2cac/README.md).

Never treat an absent or unverified asset as a baseline result. CPU prep job completion and its asset manifest are prerequisites for the evaluator.
