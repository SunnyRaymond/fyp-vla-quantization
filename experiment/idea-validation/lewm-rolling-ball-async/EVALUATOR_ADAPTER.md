## Shared control and timing path

Every mode advances simulated time only via one native `env.step()` per 40 ms control tick, preserving the configured event cadence. Before every step, hold the latest absolute 8-D target and recompute the relative command from current joints:

```text
arm_delta = (absolute_target[:7] - current_arm_joints) / 0.1
gripper = +1 if absolute_target[7] > 0.5 else -1
```

This avoids repeatedly applying a stale relative delta while waiting. All schedules share observation capture, request construction, action conversion, `env.step()`, done processing, and native success accounting.

| Mode | Frozen schedule |
| --- | --- |
| `sync` | Blocking planner request while simulation is frozen; apply the response at the next control step. |
| `fixed-delay` | Blocking request while simulation is frozen, then exactly K hold `env.step()` ticks, then apply that response. Planner wall latency does not add or subtract simulated delay. K is fixed at 0, 1, 2, 4, 8, or 16. |
| `true-async` | At most one HTTP future; step at absolute 40 ms wall deadlines while holding the last target. Promote a completed result only at a boundary. Do not queue stale requests or skip steps. Drain and mark any terminal-time unapplied future as dropped before native reset. |

The default design uses 50 ordered seeds `2026092700..2026092749`: first a 3-episode synchronous capability smoke, then synchronous 50, fixed delays over the same 50, and true-async 50. The 50-episode pilot is not a power-analysis claim. If synchronous control fails all episodes, preserve that result; do not retune the frozen model or CEM budget to force an improvement.

Each request records camera capture start/end wall time, capture sim time/control tick, request start and client response-arrival wall times, server `latency_s` and `cem_latency_s`, first-action apply wall/sim time/tick, wall/sim observation age, deadline status, and whether the response was applied or dropped. Episode records include actual sim elapsed, active wall time through the terminal `env.step()`, post-step terminal cleanup separately, measured RTF, control ticks, deadline misses, pacing overruns, and native success/phase/end reason. Client arrival time is kept separate from server Unix timestamps.
