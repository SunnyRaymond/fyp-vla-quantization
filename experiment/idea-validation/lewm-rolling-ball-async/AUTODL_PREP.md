# AutoDL RTX 4090 preparation route

Status: **read-only preparation; no instance has been rented or accessed**. This is a candidate install recipe for the pinned Rolling Ball evaluation, not a verified compatibility result. The frozen ReflexBench source is commit [`8bb931485093c6d98f8729774ad01bf824964e16`](https://github.com/LxRoboticsLab/ReflexBench/tree/8bb931485093c6d98f8729774ad01bf824964e16).

## Candidate machine and software

Use an Ubuntu 22.04 x86_64 instance with one RTX 4090 (24 GB, RT cores), at least 8 vCPUs, 64 GB RAM, and preferably 500 GB SSD. Isaac Sim 5.1.0 lists 32 GB RAM, 16 GB VRAM, and 50 GB storage as minimums; its “good” tier lists 64 GB RAM and 500 GB storage. Those are Isaac Sim requirements only, not a measured joint simulator-plus-LeWM requirement. A 4090 has 24 GB and RT cores, but Isaac Sim's requirements table names RTX 4080 as the minimum example and does not explicitly certify the 4090. Verify the compatibility checker on the rented instance before proceeding. Sources: [Isaac Sim 5.1 requirements](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/installation/requirements.html), [RTX 4090 specifications](https://www.nvidia.com/en-us/geforce/graphics-cards/40-series/rtx-4090/).

Use the version-matched Isaac Lab v2.3.1 and Isaac Sim 5.1.0 candidate. Isaac Lab v2.3.1 documents Sim 5.1.0, Python 3.11, and Linux driver 580.65.06 or newer as its recommended pairing. Check the provider's actual driver first; do not replace it blindly. ReflexBench's pinned `extension.toml` declares Isaac Lab extensions without version pins, and its pinned `pyproject.toml` does not select an Isaac Sim/Lab version, so this candidate still needs a first-instance smoke test. Sources: [Isaac Lab v2.3.1 installation](https://isaac-sim.github.io/IsaacLab/v2.3.1/source/setup/installation/index.html), [Isaac Lab v2.3.1 pip setup](https://isaac-sim.github.io/IsaacLab/v2.3.1/source/setup/installation/pip_installation.html), [Isaac Lab v2.3.1 release](https://github.com/isaac-sim/IsaacLab/releases/tag/v2.3.1), [pinned ReflexBench extension manifest](https://github.com/LxRoboticsLab/ReflexBench/blob/8bb931485093c6d98f8729774ad01bf824964e16/source/reflexbench/config/extension.toml), [pinned ReflexBench pyproject](https://github.com/LxRoboticsLab/ReflexBench/blob/8bb931485093c6d98f8729774ad01bf824964e16/pyproject.toml).

Keep simulator and policy-server dependencies in separate Python 3.11 environments/processes on the same host. The Isaac Lab guide installs Isaac Sim 5.1.0 and Torch 2.7.0/TorchVision 0.22.0 with CUDA 12.8, then installs Isaac Lab extensions; use `--install none` to avoid unused RL libraries. The pinned LeWM training environment uses Torch 2.8.0+cu128 and its own frozen world-model package stack, so do not combine both stacks in one environment without an explicit compatibility check. They will still share the 4090's VRAM. The policy server should bind to localhost. The formal epoch-100 checkpoint is available; policy-server startup evidence must identify that exact checkpoint because `/info` does not report its epoch.

ReflexBench itself is installed from the frozen checkout with `python -m pip install -e source/reflexbench`. Do not add its optional `[data]` extra for this online evaluation. Do not install cuRobo: it is used by planning-based demonstration collection, not by the existing policy-server evaluation path. Source: [pinned ReflexBench README](https://github.com/LxRoboticsLab/ReflexBench/blob/8bb931485093c6d98f8729774ad01bf824964e16/README.md).

## Smallest useful first smoke

Do this only after the user has rented and supplied access to the instance. First inspect Ubuntu/GLIBC, free storage, driver, GPU visibility, and the Isaac Sim compatibility checker. Then run the official Isaac Lab empty-scene tutorial as a graphics/runtime check. Next install the pinned ReflexBench checkout and verify one ordinary Rolling Ball reset produces the native fixed-camera RGB observation. Use the task's DataCollection variant with `obs_mode=vla`, `cam_names=fixed_cam`, `state_format=joint`, `control=joint_pos`, `num_envs=1`, and `ctrl_freq=25`; this is one fixed RGB image plus current robot proprioception, with an 8-D absolute joint target. Follow the pinned native reset unchanged: this source enters directly in the rolling phase. Do not stage a phase-0 gate wait or manually set the ball, catcher, phase, or success state. Pinned task/evaluator sources: [native evaluator](https://github.com/LxRoboticsLab/ReflexBench/blob/8bb931485093c6d98f8729774ad01bf824964e16/scripts/evaluation/eval.py), [Rolling Ball task README](https://github.com/LxRoboticsLab/ReflexBench/blob/8bb931485093c6d98f8729774ad01bf824964e16/source/reflexbench/reflexbench/tasks/manager_based/rolling_ball_interception/README.md), [fixed-camera config](https://github.com/LxRoboticsLab/ReflexBench/blob/8bb931485093c6d98f8729774ad01bf824964e16/source/reflexbench/reflexbench/tasks/manager_based/rolling_ball_interception/config/franka/data_collection_env_cfg.py).

For interface-only smoke, a local dummy policy may return the current absolute joint target once; verify that a real fixed-camera image and allowed robot proprioception reach the policy endpoint and that one 8-D target is applied through one native `env.step()`. This checks wiring, not LeWM, CEM, task success, timing, or paired evaluation. The frozen evaluator protocol additionally requires the later `eval_rolling.py` scheduler for sync, exact fixed-delay ticks, and true-future wall pacing; the pinned upstream evaluator alone does not implement all of those gates. Keep simulator `dt=10 ms` and decimation 4 (one `env.step()` per 40 ms control tick). The eventual true-future stage must pace at RTF 1 and record overruns; the interface smoke is not evidence for it.

The formal epoch-100 checkpoint is available. The first combined-GPU smoke should load it with the frozen planner settings and log simulator plus policy-process VRAM/throughput. A failure to fit both processes is a resource limitation to report, not a reason to silently shrink the frozen CEM budget. Isaac Sim explicitly cautions that Isaac Lab and sensor workloads may require more resources than its standalone minimums; 24 GB does not guarantee the combined workload will fit.

Use the task's native reset exactly as implemented in the pinned source. In this snapshot it initializes the task directly in its rolling state; do not force a README-described phase-0/gate-wait state or edit task buffers to stage a catch.

## Access and execution boundary

No AutoDL login, instance creation, package installation, download, model load, rendering, or simulation has been performed. No SSH endpoint or provider image/driver was available to verify. `eval_rolling.py` now has an explicit `--rented-host` path requiring the supplied exact Linux hostname, rejecting inherited PBS variables, and checking for an RTX 4090; its default path remains guarded by genuine PBS job/nodefile membership. This guard is statically implemented but has not been exercised on a rented instance. Keep all runtime actions behind the explicit rented-host mode.

The remaining facts to confirm on the actual instance are provider image/driver, Isaac compatibility-checker result, camera render, coexistence of simulator and policy memory, checkpoint loading, and the evaluator's timing/paired-reset gates. Until those pass on RTX, this is an install candidate only; it makes no claim that the task runs or succeeds.
