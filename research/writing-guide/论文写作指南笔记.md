# 论文写作指南笔记

来源：南京大学郭兰哲老师组 [Research-Starter-Kit](https://github.com/LAMDA-NeSy/Research-Starter-Kit) 中「如何写论文？」系列飞书文档（2026-11-01 读取）。
这里是按主题重新组织、压缩过的学习笔记，不是原文转录。原文有大量示例截图（优秀摘要、teaser 图、主表、曲线），看图时请打开各节标题下的原文链接。

---

## 0. 全局视角：一篇论文要让审稿人迅速回答三个问题

1. 这篇论文解决了一个什么样的**重要**问题？
2. 现有方法为什么**不够**？
3. 你的方法好在哪里、**好多少**？

Abstract、Introduction、Teaser 图、主表都在回答同样三个问题，只是详略不同。审稿人第一遍通常只看标题、摘要和图表，所以这几处决定第一印象。

贯穿全文的一条主线：**问题 → 方法 → 实验必须闭环**。摘要里说解决了什么问题，实验就要专门证明这个问题被解决了，而不是只报一个总体 accuracy。

## 1. Abstract —— 一份「贡献说明书」

[原文](https://dy8q0bnq8y.feishu.cn/wiki/Tz2pwvxTyiBK0zkCVszcZmJ3nwd)

摘要不是论文简介，而是**贡献声明**：在有限篇幅里让审稿人知道你解决了什么问题、关键思想是什么、对领域有什么意义。宁可短，不要全。

### 五句话结构

| 要素 | 篇幅 | 要点 |
|---|---|---|
| 背景 Context | 1 句 | 直接点出方向和任务，不铺垫常识 |
| 科学问题 Problem | 1–2 句，**最关键** | 现有研究的痛点；要上升为**结构性问题**，不能停在经验现象 |
| 方法 Method | 1–2 句 | 只讲核心思想（新架构？新损失？新数据？），并让人看出它**为什么逻辑上能解决**上面的问题 |
| 结果 Results | 1 句 | 具体可量化：几个数据集、对比谁、什么指标、提升多少 |

关于「问题」这一句，原文的提醒很重要：
- 「LLM 在某任务上经常失败」属于**经验现象**，读起来像修修补补，容易直接落进 borderline。
- 要从现象追到机理：是理论缺陷？泛化差？鲁棒性不足？还是训练/推理之间的某种结构性 trade-off？

关于「结果」这一句：
- 「significant performance improvement」任何论文都能写，等于没写。
- 结果要**回应你提出的问题**：声称解决鲁棒性，就报告在什么扰动下鲁棒性提升了多少。

### 原文分析的三个范例（ICML 2025）

- *Train for the Worst, Plan for the Best*（Outstanding Paper）：从问题分析出发；问题一句话说得非常本质（训练期复杂度与推理期灵活性的权衡）；结果是数量级的跃升，并与大得多的模型对比。
- *Lossless Speculative Decoding for Heterogeneous Vocabularies*（Oral）：最常见的「现有方法有某个限制」型论文。1 句背景（推理加速重要）→ 2 句问题（要求 drafter 与 target 共享词表）→ 1 句方法（去掉这个约束）→ 结果直接回应问题（无约束下的加速倍数）。
- *LLM-SRBench*（Oral，benchmark 论文）：问题是「现有评测反映不了真实能力」；方法部分用数字描述 benchmark 的规模、领域、类别；原文指出若把「several SOTA methods」换成「评测了几类方法、多少个模型」会更好。

## 2. Introduction —— 摘要的扩写版

[原文](https://dy8q0bnq8y.feishu.cn/wiki/ULATwBu2MiLqqRkXxV6c2S7AnPd)

逻辑与摘要相同：**研究领域 → 已有工作 → 未解决问题 → 本文工作**。

### 四个任务

1. **为什么这个领域重要**：应用价值、近年受关注的原因、基本概念。不要一开头就写自己的方法。
2. **别人做了什么**：只挑与本文最相关的路线，是为后面的 gap 做铺垫，不是文献综述。
3. **还缺什么（全篇关键）**：要回答「已有工作这么多，为什么还需要这篇」。
   - 禁止只写「this problem remains challenging」——要说清楚难在哪里：哪类场景失败、哪个假设不成立、哪种能力没被测到、哪种代价太高、哪个机制不清楚。
4. **本文做了什么**：目标、方法、贡献、与已有工作的区别。这一段要直接，不要再铺垫。

### 段落组织

- **一段一个观点**，每段第一句是主题句，后面的句子都围绕它。
- 常规 4–6 段：大背景 → 已有工作 → 不足/gap（收窄到本文关注点）→ 本文方法 → 贡献（2–4 条，具体、可验证）→ 论文结构（ML 会议一般可省）。

### 可复用骨架

1. 近年来 X 在 Y 领域越来越重要，其核心在于……，对……有重要意义。
2. 已有研究主要从……角度入手：A 关注……，B 进一步……。
3. 然而现有研究存在一个关键限制：……。具体而言……，因此在……场景下难以……。
4. 为此，本文提出……；我们设计/构建/分析……，并通过……验证。
5. 主要贡献：第一……；第二……；第三……。

### 各段常用句式功能

- 重要性：*X plays a central role in … / X has received increasing attention due to …*
- 已有工作：*Existing approaches typically rely on … / Recent work has shown that …*
- Gap：*A key limitation of current approaches is … / To date, few studies have systematically examined …*
- 本文：*In this paper, we propose … / Our approach differs from previous work in …*

## 3. Related Work —— 画地图，标出自己的位置

[原文](https://dy8q0bnq8y.feishu.cn/wiki/CLSAwWm6qifjwQkTd82czgMNnYf)

公式：**Related Work = 分类 + 概括 + 代表工作 + 局限 + 本文定位**。
它要回答：别人做了什么？我们和他们什么关系？为什么还需要我们？

- **和 Introduction 的分工**：Introduction 讲故事、建立动机；Related Work 画地图、说明位置。如果 Introduction 已经讲了动机，这里就展开技术路线和差异，不要重复。
- **组织方式**：按研究方向分小节（大多数论文适用）；或在问题已有大量方法时按技术路线分，重点比较各路线的假设、优势和限制。
- **每段四步**：概括一个方向 → 列代表工作 → 总结共性 → 指出局限 / 与本文的关系。

### 避坑

- 不要逐篇平铺「A 做了…，B 做了…」，要把 A、B、C 归为一类，说它们共同解决了什么、共同缺了什么。
- 语气客观：目的是定位本文，不是证明别人都不行。
- 引用多不等于写得好，分类清楚更重要。
- 不能只写相似工作而不写差异——读者最想知道你和它们到底哪里不同。

### 本文与已有工作的五种关系

不一定非要说「我们更好」，可以更精确地定位：**Extension**（扩展到新场景/任务/模型）、**Complement**（互补，例如别人做方法、我们做评测）、**Contrast**（假设、任务定义或目标不同）、**Unification**（统一分散的问题或方法）、**Re-evaluation**（重新评估，发现过去评测的遗漏或偏差）。

### 对比表

多维度比较已有工作时适合用表，但**维度必须是领域公认、且和核心问题直接相关**的。不要临时拼凑「我们有、别人没有」的特征，审稿人一眼就看得出是在制造差异。Benchmark 论文可参考 MMMU 的相关工作对比表（覆盖学科、子领域、图像类型等）。

## 4. Methods —— 先总后分，让读者先看到全貌

[原文](https://dy8q0bnq8y.feishu.cn/wiki/CtiAwh1eOiqOfCkPKVLc0WsxnZg)

### 推荐结构

1. **Overview**：核心思想、出发点、由哪些模块组成、每个模块干什么、输入到输出的整体流程。与主图配合：**主图让读者看见方法，Overview 让读者看懂这张图**。
2. **Problem Formulation**：单独一节定义输入、输出、数据、模型、目标和全部符号。AI 论文符号多，不先定义清楚后面公式没法读。
3. **Method Details**：按模块展开，每个模块依次说明：解决什么问题 → 输入 → 怎么处理 → 输出 → **为什么这样设计**。只有模块名和公式是不够的。
4. **Training / Optimization**：训练目标和优化方式。
5. **Inference / Deployment**：测试或使用时怎么跑。

### 公式三件事

1. 公式**前**说明为什么需要它（*To model …, we define …*）。
2. 公式**后**解释每个关键符号（*where … denotes …*）。
3. 再说明它在方法里起什么作用（*This objective encourages the model to …*）。

另外：符号首次出现必须定义；同一符号全文只表示一个意思；不要堆不必要的下标；公式是为逻辑服务的，不是为了显得数学化。

### 伪代码

流程复杂时可以加 Algorithm，但它不能替代正文：正文先讲目的 → 伪代码给完整流程 → 正文再解释关键步骤和设计理由。伪代码里的变量名和正文符号保持一致。

### 写清 novelty

在关键模块处简要说明：和已有方法有何不同、为什么需要、解决了什么具体问题、没有它会怎样。Methods 里点到即止，**详细对比和效果证明放到 Experiments**。

## 5. Experiments —— 每个实验都服务于一条 claim

[原文](https://dy8q0bnq8y.feishu.cn/wiki/KHgSw2MkrikxlskGe5qclkdbn2c)

常见结构：Setup → Main Results → Ablation → Analysis → Case Study / Visualization → Robustness / Generalization → Efficiency / Cost。不必全有，**结构服务于贡献，而不是为了显得实验多**。

- **Setup**：数据集/benchmark、baseline、指标、实现细节、训练与推理参数、重复次数/随机种子/统计方式、比较是否公平。具体，不含糊；细节太多放附录。
- **Main Results**：对应主表主图。回答：是否优于已有方法、在哪里提升明显、哪些结果最能支撑贡献、哪里没有提升。**不要只写「Table 1 shows the results」，要告诉读者应该从表里看出什么**。
- **Ablation**：证明关键设计不是随手加的——去掉、替换某模块，换训练目标或策略，改数据量/规模。围绕**设计动机**来写。
- **Analysis**：解释方法的行为——按类别、难度、数据规模、模型规模、错误类型、超参数敏感性等拆开看。目标是回答「什么时候更好、为什么更好、什么时候不够好」，不是重复主表。
- **Case Study**：数字说不清、需要展示输出质量、比较行为差异、展示失败案例或任务难度时使用。

### 写作细节

1. **主动引导读者看图表**（*As can be seen in Fig. 1 …*），不要假设读者会自己去看。
2. **挑重点描述**：你详细描述哪个结果，读者就认为哪个重要。
3. **用评价性语言**解释数字的含义，不要让原始数据自己说话。
4. **正视异常**：不提异常显得外行；正确做法是承认 + 弱化影响 + 转回正面结论。常用弱化词：*slightly, somewhat, a minor deficit, negligible, it should be noted that …*

## 6. 论文画图

[原文](https://dy8q0bnq8y.feishu.cn/wiki/OGpcw6zaRiQ6OwkNxfYcl7IKnBh)（本节示例图最多，强烈建议对照原文看图）

三类图：**动机图（Teaser）**、**方法图（主图、架构图、数据构造图）**、**实验图（表、柱状图、折线、散点、热力图、案例可视化）**。前两类可以先让 AI 出草图再用 PPT/Visio 等复刻精修；实验图可以让 coding agent 写绘图代码。

### 动机图 Teaser

- 放在开头或 Introduction，只围绕两件事：**问题/观察**（现有方法的局限、典型或反直觉的失败案例）和**本文优势**。
- 动手前先写下一句话：**读者看完这张图应该记住什么？** 这句话想不清楚，图也画不清楚。
- **Self-contained**：只看这张图、不翻正文也能懂。
- 常见套路：现有方法 vs 本文方法的左右对比；抽象形象化的对比；用一个具体样本/场景串起整个方法；工作量概览（适合 benchmark 或工程量大的工作）。

### 方法主图

目标：让读者看懂整个工作流和核心贡献。

画图流程：
1. 先写一句话作为 caption，说明这张图要表达什么。
2. 列出必须出现的元素和它们之间的流转关系。
3. 定布局：上下分层、左右对比还是闭环？主流程从上到下还是从左到右？核心贡献放哪？
4. 模块化并命名：每块有清晰的输入输出，名字简短，**与正文术语一致**。
5. 统一视觉语言：颜色、形状、箭头、字体、图标风格。

原则：
- 像写代码一样模块化。
- 不同含义的箭头用不同样式（如实线主流程、虚线反馈、红色监督信号、灰色辅助信息）。
- 同类模块同色；颜色控制在 3–5 种，低饱和度。
- 可以在图上方加 legend 说明各种框和箭头的含义（原文推荐的 WAPITI 例子）。
- 适当加入小图标、卡通元素增加信息量和美观。原文特别推荐 V-IRL 整篇的配图。
- Benchmark 主图通常按数据构建、评估指标、被测模型、主要发现来划分模块。

### 结果图表

- **相关工作对比**（benchmark 常用）：选定维度，用符号或文字逐项对比；也可以把各 benchmark 画在「深度 × 广度」等二维图上。
- **主结果表**：目标是**让读者最快找到本文方法，并看清超过了哪些 baseline**。
  - 最优加粗、次优下划线（或底色、双线/单线等区分名次）；
  - 相同 backbone/设置放同一 block，按 benchmark/指标做列分组；
  - caption 直接写主要结论；
  - 表不要太空：行列间距过大会显得内容单薄，可以调整布局或补充方差等信息。
- **曲线图**：展示某个变量变化时各方法的性能趋势；可以在曲线上标注提升幅度，用阴影带表示方差。

### 工具与技巧

- **配色**：简约、低饱和，忌纯红绿蓝。可基于 PPT 默认色盘微调；工具有 ColorKit、ColorBrewer 2.0（可选色盲友好/打印友好）、SciVisColor、Adobe Color。
- **立体感**：阴影、虚实线条变化。
- **图标库**（同一张图里保持同一风格，最好用同一个 icon pack）：Flaticon、iconfont（阿里）、The Noun Project、BioRender（生物医学）。
- **流程图工具**：draw.io / diagrams.net（免费，可导出可编辑的 SVG/PDF）、ProcessOn、Lucidchart。
- **绘图代码库**：Seaborn + Matplotlib、ProPlot（多子图排版与学术配色）。
- **AI 草图**：用图像模型生成 teaser/流程图的布局灵感，提示词里写清结构，例如「从左到右三段式、干净背景、柔和配色、矢量风格」。
- **素材铁律**：优先下载 `.svg` / `.eps` / `.pdf` 矢量格式，缩放到双栏尺寸也不糊；注意图标的授权协议（如 CC BY 需署名）。
- 延伸阅读：Datawhale [《科研论文配图绘制指南》](https://github.com/datawhalechina/paper-chart-tutorial)。

## 7. Reference —— 每一条 bib 都要手工整理

[原文](https://dy8q0bnq8y.feishu.cn/wiki/A4q2wSnmRi91rykHke1cQIhnnAh)

从 Google Scholar / DBLP 复制下来直接贴是不行的，必须逐条编辑，保证格式正确且统一。

### 整理步骤

1. 从 DBLP 复制 bib。
2. **改 key**：统一用「作者姓 + 年份 + 关键词」，如 `zhou2024symagent`，不要保留 `DBLP:conf/icml/ZhouL24`。
3. **条目类型**：会议 `@inproceedings`，期刊 `@article`。
4. **删无用字段**（publisher、url 等），一般只保留 author、title、booktitle/journal、volume、number（期刊）、pages、year。
5. **大小写保护**：BibTeX 会把标题转小写，专有名词和模型名要用 `{}` 包起来，例如 `title = {{GPT}-4o mini}`、`{{LLM-SR}: {S}cientific Equation Discovery}`。
6. **作者**：尽量列全，实在太多再用 et al.；名字沿用 DBLP 格式即可。
7. **booktitle / journal**：同一会议在全文中必须完全一致（全称/缩写、大小写都统一）。
   - 大多数会议写成 *Proceedings of the Nth International Conference on …*，序数词别写错（1st, 2nd, 3rd, 4th…）；
   - 按年份而非届数的会议（如 EMNLP *Proceedings of the 2024 Conference on …*、CVPR *Proceedings of the IEEE/CVF Conference on Computer Vision and Pattern Recognition*），保持一致即可；
   - NeurIPS 写 *Advances in Neural Information Processing Systems*，**删掉后面的卷号数字**；
   - 会议名每个实词首字母大写。
8. **期刊**：volume、number、pages 要齐全。
9. **pages**：ICLR 等没有页码的会议除外，其他保持一致、不要缺。

### 投稿前自检

- [ ] 无关字段（publisher、url 等）已删除
- [ ] 标题大小写风格统一，专有名词已加 `{}`
- [ ] 作者写全或统一用 et al.，无大小写混乱
- [ ] 同一会议/期刊名格式完全一致，无多余数字
- [ ] 期刊引用有卷号、期号
- [ ] 除 ICLR 等外，页码不缺
- [ ] 没有重复条目

## 8. Rebuttal —— 一盘需要统筹的棋

[原文](https://dy8q0bnq8y.feishu.cn/wiki/M9d1wv5Efi2aG4kH4IDc5zqVnQh)

### 原则

- **有问必答，不漏点**。篇幅不够可以合并相似意见，但绝不能悄悄删掉某个问题——被发现会在 discussion 阶段被当成硬伤。
- **揣摩各审稿人倾向，分配笔墨**：
  - 写明「解决了 X 就加分」的，务必全力争取；
  - 正面审稿人：巩固；borderline：重点争取；负面审稿人：投入最多篇幅去澄清；
  - 一位审稿人说 novelty 不足、另一位说 novel 时，把后者的评价拿来用。
- **全局统筹**：rebuttal 要和正文、各条 review 配合，篇幅优先给最关键的审稿人和问题；能缩写就缩写。
- **抓住审稿人的事实错误**（明显错误的观点、要求对比并非领域常用的数据集等），回应时先指出，抢占主动——其他审稿人和 AC 都会看到；也可以写进 AC message，降低该意见的可信度。

### 常见问题怎么回

- **Novelty 不足**（与已有方法差异小 / A+B 组合）：重新梳理贡献，说明组合并非 trivial，再从 motivation 和 intuition 换个角度讲亮点；也可以强调其他部件或整体范式是新的，或者突出简单有效、SOTA。
- **事实错误**（确实是我们错了）：大方承认、致谢、承诺在 final version 更正。若是写作不清导致误解，承认表述问题并解释实际做法。
- **提升有限**：
  1. 引用同类顶会工作，说明相对 baseline 的提升幅度是可比的；
  2. 找出提升特别明显的重要场景单独展示；检查是否有不公平设置，能补公平对比就补；
  3. 强调其他好处：效率、通用性、鲁棒性等。
- **实验不充分**：能补就补；规模太大来不及就承诺 final version 补上；不合理的要求，用文献等证据说明为什么不需要。
- **语法、结构、漏引**：承认、感谢、修改。

### AC Message

审稿人明显不专业、不熟悉领域、自相矛盾或带有严重偏见时，可以给 AC 写信请其注意。三种典型写法：
- 违背领域常识（且该审稿人自评「very confident」）；
- 自相矛盾（列出互相矛盾的具体评论编号）；
- 对本文贡献有明显偏见。

### 常用表达（按功能）

- **开头**：*We sincerely thank all reviewers and ACs for their time and efforts. Common questions are addressed first, followed by individual responses.*
- **同意**：*We thank the reviewer for pointing out this issue. We will revise … in the final version.*
- **不同意**：*We respectfully disagree that … / The reviewer might have overlooked Table N … / We believe … would be outside the scope of this paper because …*
- **澄清**：*We have indeed reported/discussed … in the original paper (cf. Line N).*
- **补充**：*We have included a new table (cf. Table N) to further illustrate …*

延伸阅读：[Paper-Rebuttal-Tips](https://github.com/MLNLP-World/Paper-Rebuttal-Tips)、魏秀参老师《浅谈学术 Rebuttal》。

## 9. 套到我们的 CVPR 论文上

按论文 C1（未来 latent 保真度）→ C2（RAVQ）→ C3（结果）的主线，对照上面各节，写作时重点检查：

1. **摘要的「问题」句要讲结构性问题**。不要写「量化后 VLA 成功率下降」这种现象描述，而要写机理：weight-only VQ 在 W2 下破坏了**未来 latent 的保真度**（C1），而现有量化目标只看当前层或当前步的重建误差，看不到这一点。
2. **方法句要让人看出它为什么能解决这个问题**：RAVQ 把 C1 指出的未来 latent 敏感度变成 QTIP 量化步骤中的预算分配。只写「我们提出了一种新的量化方法」不够。
3. **结果句要和 C1 闭环**：除了闭环成功率，还要报告和「未来 latent 保真度」直接对应的指标，否则摘要声称的问题在实验里没有被证明解决。
4. **Introduction 第 3 段（gap）要具体**：说清楚已有 W2 方法（QTIP / QuIP# / GPTVQ）在什么假设下失效，避免空泛的「remains challenging」。
5. **Related Work 用「Contrast / Complement」来定位**：说明我们和通用 LLM 量化方法在**优化目标**上不同，而不是说它们都不行。GuidedQuant 只放这里。
6. **实验结构对齐贡献**：主表（W2/W3 × 各 host × BF16）→ 消融（RAVQ ①–④）→ 分析（收益出现在哪些 bit 宽和任务上，什么情况下不起作用）。主表 caption 直接写结论；同 bit 宽放同一 block；最优加粗、次优下划线。
7. **结果有不显著的地方要正视**：按第 5 节的「承认 + 弱化 + 转回正面」处理，不要回避。
8. **bib 投稿前按第 7 节自检一遍**，尤其是 CVPR / NeurIPS / ICLR 的 booktitle 是否统一。
